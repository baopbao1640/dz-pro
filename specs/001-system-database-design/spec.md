# System Management Database Design Spec

## 1. Background

Platform Core is currently a modular monolith foundation. The system management domain must define a stable database model before implementing user management, department management, role-based access control, dictionary/configuration management, notices, audit logs, and scheduled jobs.

Authentication is owned by Keycloak. The local system database only stores business user mappings, platform organization data, roles, permissions, and operational metadata.

## 2. Goals

- Define the system management domain database tables before writing business code.
- Support Flyway-managed schema creation and future schema evolution.
- Provide RBAC data structures for users, roles, menus, buttons, and data permissions.
- Keep authentication separate from local business user records.
- Ensure log tables do not block or slow down main business flows.
- Keep the design compatible with the current modular monolith boundary.

## 3. Non-Goals

- Do not implement Java business code.
- Do not implement Vue pages.
- Do not implement local username/password login.
- Do not replace Keycloak.
- Do not introduce Spring Cloud.
- Do not use ORM auto DDL or automatic table creation.
- Do not define business-domain tables outside the system management scope.

## 5. Common Table Rules

All business tables must be created and changed through Flyway migrations.

Primary key strategy is fixed for all tables:

- Column name: `id`
- Type: `bigint`
- Generation location: application side
- MyBatis Plus strategy: `ASSIGN_ID`
- Algorithm style: Snowflake-style distributed ID

The following primary key strategies are forbidden:

- UUID primary keys
- Auto-increment primary keys
- Mixed primary key strategies across system management tables

Business tables must include unified audit fields:

| Column | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `bigint` | Yes | Primary key generated by application-side MyBatis Plus `ASSIGN_ID`. |
| `create_by` | `varchar(64)` | No | Creator local user ID. Stores `sys_user.id` as a string. |
| `create_time` | `timestamp with time zone` | Yes | Creation time. |
| `update_by` | `varchar(64)` | No | Last updater local user ID. Stores `sys_user.id` as a string. |
| `update_time` | `timestamp with time zone` | No | Last update time. |
| `remark` | `varchar(500)` | No | Operational remark. |

`create_by` and `update_by` must not store Keycloak token values, Keycloak subject values, email addresses, or display names.

Soft-delete-capable business configuration tables should additionally include:

| Column | Type | Required | Description |
| --- | --- | --- | --- |
| `del_flag` | `char(1)` | Yes | `0` normal, `1` deleted. |

Append-only log tables use a reduced event-field model and must not include the full unified audit field set. `sys_oper_log`, `sys_login_log`, and `sys_job_log` must not include `update_by`, `update_time`, `remark`, or `del_flag`.

Recommended status flags:

- `status`: `0` normal, `1` disabled
- `del_flag`: `0` normal, `1` deleted
- Boolean fields should use `char(1)` with `Y` and `N` where cross-database readability matters.

## 6. Authentication Boundary

`sys_user` is a business user mapping table, not a local authentication table.

Keycloak owns:

- Login
- Passwords
- Password reset
- MFA
- External identity providers
- Session lifecycle
- Token issuing

`sys_user` owns:

- Mapping to Keycloak subject
- Internal display name
- Department and post relationship
- Local enable or disable status
- Platform-specific user metadata

`sys_user` must not store password hashes, salts, password reset tokens, login sessions, or MFA secrets.

`sys_user` must not store:

- Passwords
- Password hashes
- Password salts
- Sessions
- Refresh tokens
- Access tokens
- MFA secrets
- MFA recovery codes

## 7. RBAC Model

The RBAC model uses:

- User to role: `sys_user_role`
- Role to menu/button permission: `sys_role_menu`
- Role to department data scope: `sys_role_dept`
- Menu table as permission resource tree: `sys_menu`

`sys_menu` supports three resource types:

- `M`: directory
- `C`: menu
- `F`: button or function permission

Roles support data permission scope through `data_scope`.

Recommended `data_scope` values:

- `1`: all data
- `2`: custom departments
- `3`: current department
- `4`: current department and child departments
- `5`: current user only

When `data_scope = 2`, allowed departments are defined in `sys_role_dept`.

## 7.1 Unique Index and Soft Delete Rule

Business tables with unique constraints and `del_flag` must avoid conflicts with soft-deleted records.

For PostgreSQL, active-record uniqueness should use partial unique indexes with `WHERE del_flag = '0'`.

This rule applies at minimum to:

- `sys_user`
- `sys_role`
- `sys_post`
- `sys_dict_type`
- `sys_config`

Example:

```sql
CREATE UNIQUE INDEX uk_sys_role_role_key_active
ON sys_role (role_key)
WHERE del_flag = '0';
```

## 9. Relationship Summary

- `sys_user.dept_id` references `sys_dept.id` logically.
- `sys_user_role.user_id` references `sys_user.id` logically.
- `sys_user_role.role_id` references `sys_role.id` logically.
- `sys_user_post.user_id` references `sys_user.id` logically.
- `sys_user_post.post_id` references `sys_post.id` logically.
- `sys_role_menu.role_id` references `sys_role.id` logically.
- `sys_role_menu.menu_id` references `sys_menu.id` logically.
- `sys_role_dept.role_id` references `sys_role.id` logically.
- `sys_role_dept.dept_id` references `sys_dept.id` logically.
- `sys_dict_data.dict_type` references `sys_dict_type.dict_type` logically.

The platform adopts a logical foreign key plus application-layer validation strategy.

Current phase rules:

- Do not use PostgreSQL physical foreign keys.
- Use logical relationships in schema design and application validation.
- Use indexes to preserve query performance.

Reasons:

- Reduce migration complexity.
- Reduce restrictions during batch imports.
- Reduce module coupling.
- Improve operational flexibility.

## 10. Flyway Requirements

- Initial system management schema is implemented in `platform-core/platform-admin/src/main/resources/db/migration/V2__create_system_management_tables.sql`.

- PostgreSQL-compatible SQL should be used unless the project formally changes database target.

## 11. Initial Seed Data Requirements

The first Flyway implementation phase must initialize the minimum platform system management data.

Required seed data:

- Super administrator role.
- `system` management directory.
- User management menu.
- Role management menu.
- Menu management menu.
- Department management menu.
- Post management menu.
- Default administrator user mapping.
- Basic dictionary types.

Seed data constraints:

- Do not create a default password.
- Do not create local authentication logic.
- The default administrator mapping uses temporary `keycloak_user_id = 'admin-keycloak-sub'`.
- Seed IDs use fixed `bigint` values starting from `1000000000000000001`.
- Fixed seed IDs must remain compatible with the application-side MyBatis Plus `ASSIGN_ID` bigint strategy.

Basic dictionary types initialized by the first migration:

- `sys_normal_disable`
- `sys_yes_no`
- `sys_user_sex`
- `sys_notice_type`
- `sys_job_status`

Default log retention policy:

- Operation logs, login logs, and job logs are retained for 180 days by default.
- The first migration stores this value in `sys_config` as `sys.log.retention.days = 180`.
- Current phase does not create PostgreSQL partitions.
- Future implementation may add monthly archive, partitioning, and cold-data cleanup.

## 12. Acceptance Criteria

- The feature directory contains `spec.md`, `plan.md`, `tasks.md`, and `progress.md`.
- The design covers all 17 required tables.
- All primary keys use `bigint` and application-side MyBatis Plus `ASSIGN_ID`.
- UUID, auto-increment, and mixed primary key strategies are forbidden.
- `sys_user` does not include password, salt, session, refresh-token, or MFA-secret fields.
- Business tables include unified audit fields.
- Append-only log tables use reduced event fields and omit `update_by`, `update_time`, `remark`, and `del_flag`.
- RBAC relationships are explicitly defined.
- `sys_menu` supports directory, menu, and button/function permission types.
- `sys_role` supports data permission scope.
- The relationship model uses logical foreign keys plus application-layer validation.
- Unique constraints on soft-deleted business tables use PostgreSQL partial unique indexes.
- Log table performance rules are documented.
- Log table future archive, partition, and cold-data cleanup capability is documented, while current phase does not use PostgreSQL partitioning.
- Flyway-only schema management is documented.
- Quartz is confirmed as the scheduler technology for later implementation.
- Initial seed data requirements are documented.
- The first Flyway migration phase creates the 17 system management tables and required seed data.
- No Java or Vue business code is created.
- No Spring Cloud dependency or service split is introduced.
- No automatic table creation is proposed.

## 13. Confirmed Decisions

- Primary key strategy: `bigint`, application-side MyBatis Plus `ASSIGN_ID`, Snowflake-style ID.
- Foreign key strategy: no PostgreSQL physical foreign keys; use logical foreign keys plus application-layer validation.
- Audit identity strategy: `create_by` and `update_by` store local `sys_user.id` as `varchar(64)`.
- Log partition strategy: no PostgreSQL partitioning in the current phase; reserve future monthly archive, partitioning, and cold-data cleanup.
- Log retention strategy: default retention is 180 days.
- Scheduler technology: Quartz.
- Seed data: fixed bigint IDs starting from `1000000000000000001`, default administrator `keycloak_user_id = 'admin-keycloak-sub'`, required system menus, super administrator role, default administrator mapping, and basic dictionary types.

## 14. Open Questions for Later Implementation

- Decide whether additional button-level menu permissions should be seeded in a later permission-management feature.
- Decide when log monthly archive, partitioning, and cold-data cleanup should be implemented.
