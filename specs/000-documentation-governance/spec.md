# Documentation Governance Spec

## 目标

建立平台级 Spec、Progress、Phase 文档治理规范，解决长期演进中出现的英文流水日志过多、Agent 痕迹过重、架构决策缺失、Deferred 与技术债记录不足、文档风格不统一等问题。

本规范只治理文档流程，不引入 Java、Vue、Mapper、Service、Controller、XML、Flyway、OpenAPI 或新业务功能。

## 适用范围

适用于所有 `specs/<number>-<feature>/` 功能目录，包括现有功能、后续新增功能、跨 Agent 协作功能和阶段性重构任务。

每个功能目录必须保留四个核心文件：

- `spec.md`：描述需求、边界、验收标准、领域规则和约束。
- `plan.md`：描述技术方案、阶段拆分、关键决策、验证策略和不做事项。
- `tasks.md`：描述可执行任务清单、阶段状态和验证门禁。
- `progress.md`：描述当前阶段状态、已实现能力、架构决策、Deferred、风险、技术债和下一步计划。

## progress.md 标准结构

所有 `progress.md` 必须采用以下一级标题，顺序固定：

```markdown
# 当前阶段

# 当前目标

# 当前完成情况

# 当前架构决策

# 已实现能力

# Deferred（暂缓事项）

# 风险与技术债

# 下一阶段计划

# 验证结果

# Agent 协作备注
```

## 内容要求

`progress.md` 必须明确区分以下状态：

- 已经真正实现：已经有代码、SQL、配置、页面或文档产物，并通过相应验证。
- scaffold：只有骨架、占位、接口契约、无持久化实现或未接真实数据源。
- intentionally deferred：为了控制复杂度、阶段边界或依赖未就绪而故意暂缓。
- 技术债：当前可接受但未来必须处理的问题。
- 未来扩展点：后续阶段可扩展但当前不承诺完成的能力。

## 禁止内容

`progress.md` 禁止成为低价值执行日志：

- 禁止纯流水账。
- 禁止大量无意义 Agent 执行痕迹。
- 禁止全英文工程记录。
- 禁止重复粘贴命令输出。
- 禁止用“已完成”掩盖 scaffold、Deferred 或技术债。

## 文档语言规范

文档必须中文主导。

英文仅用于：

- 技术名词，例如 `Flyway`、`Keycloak`、`Quartz`。
- 类名、接口名、annotation、API、数据库字段、权限码。
- 命令、路径、文件名、配置键。

禁止大段英文叙述和 AI 执行流水。

## 架构决策记录规范

`progress.md` 必须记录“为什么”，而不仅是“做了什么”。

至少覆盖：

- 为什么这样设计。
- 为什么 defer。
- 为什么不实现。
- 为什么拆分。
- 为什么隔离。
- 当前决策的影响范围。

## Deferred 规范

`# Deferred（暂缓事项）` 用于记录当前故意未做的事项，包括：

- 当前阶段不做的功能。
- 依赖后续阶段的能力。
- 为降低复杂度而推迟的实现。
- 需要业务确认或技术验证后再做的事项。

示例：

- 动态路由真实权限联动。
- 数据权限 SQL 注入器。
- audit persistence。
- permission cache。

## 技术债规范

`# 风险与技术债` 必须记录：

- 风险描述。
- 影响范围。
- 当前接受原因。
- 后续处理方向。

技术债不能只写“后续优化”，必须说明未来怎么处理。

## 后续 Feature 强制规则

后续所有新 Feature 必须遵守 Documentation Governance：

- 开始前先读对应 `progress.md`。
- 没有 `progress.md` 时先创建标准结构。
- 每个阶段结束后更新标准结构，不追加流水日志。
- 多 Agent 协作时，`Agent 协作备注` 只记录职责边界、冲突处理和同步要求。
- 业务实现状态必须清楚标注为“已实现”“scaffold”“Deferred”或“技术债”。
