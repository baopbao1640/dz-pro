# 代码注释治理规范

本规范是强制工程规范，不是参考文档。新增和修改代码必须遵守本规范，并接受 Governance Review。

注释治理参考阿里巴巴 Java 开发手册的核心思想：注释应服务可维护性、领域理解和边界说明，不能替代清晰命名，也不能成为复述代码的噪音。

## 基本原则

- 注释必须说明对外契约、设计原因、边界条件、异常约束或非显然业务规则。
- 禁止写只复述代码含义的低价值注释。
- 禁止用注释掩盖命名混乱、职责不清或逻辑过长。
- 修改代码时必须同步检查相邻注释是否仍然准确。
- 公共接口、Service 接口、Controller 对外方法、复杂权限逻辑、审计逻辑、数据权限逻辑必须具备有效注释。

## 推荐注释

- 领域规则：说明业务约束、权限边界、数据范围含义。
- 对外契约：说明入参、返回、状态码、幂等性和调用前提。
- 设计原因：说明为什么采用当前实现，而不是只描述做了什么。
- 风险边界：说明 Deferred、临时兼容、降级策略和未来处理方向。
- 安全规则：说明认证、授权、脱敏、审计和越权防护的关键约束。

## 禁止注释

- `// 设置用户名` 这类复述赋值语句的注释。
- 与代码实际行为不一致的历史注释。
- 大段 Agent 执行记录。
- 用英文流水日志解释修改过程。
- TODO 只写“后续优化”但不说明触发条件、范围和处理方向。

## Java 注释要求

- 公共 API 使用 Javadoc 或清晰的中文说明。
- 复杂方法内部只在关键分支前添加短注释。
- 权限、审计、数据范围、事务边界和异常转换必须说明设计原因。
- Mapper XML 中的动态 SQL 如包含权限或数据范围条件，必须说明条件来源和适用范围。

## Review 要求

Governance Review 必须检查：

- 是否存在复述代码的低价值注释。
- 是否存在已经失效的注释。
- 新增公共能力是否缺少契约说明。
- 安全、权限、审计、数据范围逻辑是否缺少边界说明。
- TODO、Deferred 和技术债是否已经进入对应 `progress.md`。
